SahyogRide — New Ticket Backlog (Phase 6-8)
=============================================
Continuation of docs/TICKETS.md, starting at SAHYOG-30. Same conventions:
one ticket = one branch = one commit, acceptance criteria are the
definition of done. Read docs/API_CONTRACT.md before any ticket that
touches a response shape — every contract change below is additive
(new nullable fields), never a breaking rename.

Scope note: SAHYOG-33/34 are explicitly DEMO features for a client
presentation, not real GPS/telematics. They are simulated client-side
(no map library, no location hardware, no new backend/infra) by deliberate
decision, as a conscious, called-out exception to CLAUDE.md's "no maps"
scope rule — not a silent reinterpretation of it. All other CLAUDE.md
scope exclusions (payment, waitlist, QR, analytics dashboard, SMS/email,
admin panel, native app, i18n, microservices/Redis/Docker/K8s, model
training) still apply unchanged.

SAHYOG-44 — Fix coordinator passenger list breaking across browser tabs
branch: fix/SAHYOG-44-cross-tab-auth-sync
commit: fix(SAHYOG-44): sync auth state across tabs to stop stale-identity requests

Description:
Reported bug: a coordinator viewing their passenger list in one tab
saw it fail to load after a rider account was logged into in another
tab of the same browser. Root cause: the JWT lives in localStorage,
which is shared across all tabs of one origin - client.js already
reads the token fresh on every request, but AuthContext's `user`
state (used to gate coordinator-only routes) was only set on
mount/login/logout, so the first tab kept rendering as "coordinator"
while its requests were silently using the second tab's rider token,
surfacing as an unexplained "couldn't load the passenger list" error
rather than an honest identity change. Not a backend bug - the
backend was verified correct via direct API testing (hold -> confirm
-> passenger list all worked) before this was diagnosed.

Acceptance criteria:
- [ ] AuthContext listens for the browser's `storage` event and
      re-syncs `user` state (and clears the TanStack Query cache)
      whenever another tab changes the stored token/user
- [ ] A coordinator tab immediately reflects a role change made in
      another tab (redirected off coordinator-only routes by the
      existing RequireCoordinator guard) instead of continuing to
      render stale and failing requests silently
- [ ] No backend changes - this was purely a frontend state-sync gap
